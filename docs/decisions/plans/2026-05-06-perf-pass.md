# ferrodec performance pass + ADR audit log (1.11.0 candidate)

## Context

ferrodec's correctness work is largely settled (the 1.7.1 → 1.10.1 trail closed every reviewer-flagged item and pushed conformance to 8 622 / 0 / 99). The remaining "review backlog" needs an external driver — a real workload, profile data, or feature request. The user has decided on two:

1. **Audit-log infrastructure**: capture ferrodec's significant decisions (skipped Verus pilot, will-not-fix non-IEEE rounding, conformance-runner status threading, etc.) as Architecture Decision Records under `docs/decisions/`, plus archive the approved plans alongside. Future reviewers shouldn't have to mine commit messages or release notes to reconstruct *why* a decision was made.

2. **Performance pass**: review hot paths, expand benchmarks to fill known coverage gaps, capture a comprehensive baseline, then apply six concrete optimization candidates identified by a structured exploration of the arithmetic kernels and multiword primitives. Each candidate gets re-benched after landing so the recorded delta is real.

The two strands run in sequence — ADR scaffolding first, then perf — because the perf decisions (which candidates to keep, which to revert if neutral) belong in the audit log as they're made.

## Out of scope

- Algorithmic rewrites of `add_kernel`, `mul_finite_finite`, `div_finite_finite`. The plan targets local optimizations (precomputed tables, redundant-call elimination, early exits) rather than redesigning the alignment / rounding pipelines.
- Embedded-target profiling. ferrodec's primary perf target remains 64-bit hosts; thumbv6m benches need real hardware.
- New IEEE 754 ops or feature-flag changes. Pure perf delta on existing surface.
- Inline assembly or `unsafe`. ferrodec preserves `#![forbid(unsafe_code)]`.

## Phase 0 — ADR infrastructure (≈ 1 hour)

Establish the audit log so subsequent perf decisions land into it as they're made.

**Layout:**

```
docs/
  decisions/
    README.md         — what an ADR is, naming convention, status lifecycle
    template.md       — copy-this template for new ADRs
    0001-*.md         — first ADR
    ...
    plans/
      2026-05-06-perf-pass.md  — archived approved plans
```

**Format**: standard MADR-lite (Markdown ADR). Each file:

```md
# ADR-NNNN: <title>

- **Status**: proposed | accepted | superseded by ADR-XXXX | rejected
- **Date**: YYYY-MM-DD
- **Context**: why this decision was on the table
- **Decision**: what we decided
- **Consequences**: what follows (positive and negative)
- **Related**: PR / commit / plan references
```

**Retroactive ADRs to seed the log** (one commit, batch of files):
- ADR-0001: BID-128 over DPD-128 (foundational design choice)
- ADR-0002: Per-op `(value, Status)` over global flag word
- ADR-0003: Method-only API; opt-in `core::ops` via feature flag
- ADR-0004: Skip Verus pilot graduation (link to `verus/EXPERIMENT.md`)
- ADR-0005: Will-not-fix `half_down` / `05up` rounding directives
- ADR-0006: Defer wholesale perf optimization until profile data exists *(superseded by this plan's ADR-0007)*

The retroactive ADRs are short — each one's a 10-minute write-up of an existing decision. Their value is making the reasoning grep-able.

**Plans archive**: approved plans (this one, the Verus pilot, etc.) get copied to `docs/decisions/plans/` with date prefix when their accompanying ADR transitions to `accepted` or `superseded`. The current plan file at `~/.claude/plans/rustling-munching-moth.md` is per-session scratch; the *approved* version is what archives.

**Stop-loss**: skip retroactive ADRs if the format takes longer than expected. Just land the directory + template + ADR-0001 + this plan's ADR. Past decisions can be retroactively documented later.

## Phase 1 — bench expansion (≈ 2-3 hours)

Existing benches (`benches/{core_ops,conversions,transcendentals}.rs`) cover add/sub/mul/div/sqrt/fma at a 6×6 input matrix and a few transcendentals. Coverage gaps the perf pass needs filled before optimization, so the deltas are visible:

**To `benches/core_ops.rs`:**
- `add_alignment_heavy` / `sub_alignment_heavy`: input pairs with widely-separated quanta (e.g. `1e0` vs `1e-30`) to isolate the alignment + sub-ULP path that candidate 3a (`mul_pow10` table) most affects.
- `mul_full_precision`: two 34-digit coefficients to exercise maximum U256 product width.
- `div_magnitude_extreme`: one tiny / one huge operand to force the long-division early-exit path that candidate 3c targets.

**New `benches/comparison.rs`:**
- `partial_cmp` over a sorted-input pattern (sort-heavy workload simulation).
- `total_cmp` same shape.
- `compare_total_magnitude` same shape.

**To `benches/conversions.rs`:**
- `from_i32`, `from_u32`, `from_u64` (only `from_i128` exists today).
- `to_i32`, `to_u64`, `to_u128` (only `to_i64` exists today).

After the file edits, register the new bench in `Cargo.toml` (`[[bench]]` block, `required-features = ["fmt"]`).

**Stop-loss**: if a bench shape is non-obvious (e.g. how to construct an "alignment-heavy" pair without making it too cohort-pathological), skip it and document why in the bench file's module-level comment. Better fewer-but-faithful benches than chasing pathological inputs.

## Phase 2 — baseline capture (≈ 30 min)

Run the full bench suite and record numbers in a new ADR (`ADR-0007-perf-baseline.md`):

```sh
cargo bench --bench core_ops 2>&1 | tee /tmp/bench-baseline-core_ops.txt
cargo bench --bench comparison --features=fmt 2>&1 | tee /tmp/bench-baseline-comparison.txt
cargo bench --bench conversions --features=fmt 2>&1 | tee /tmp/bench-baseline-conversions.txt
cargo bench --bench transcendentals --features=transcendentals 2>&1 | tee /tmp/bench-baseline-transcendentals.txt
```

The baseline ADR records median / IQR per bench, the host (CPU, OS, Rust version), and the commit SHA. Later phases compare against these numbers.

## Phase 3 — apply optimization candidates

Six candidates from the structured exploration, ranked by expected impact. Each lands as its own commit so post-bench deltas attribute cleanly. After each commit, re-run the relevant bench subset and append a short measured-result note to the corresponding ADR.

Per candidate workflow: implement → run all property tests + conformance + Kani harnesses → run the relevant benches → record delta in the ADR → commit (or revert if neutral / negative).

### 3a. Precomputed `10^k` table for `mul_pow10` (highest impact)

**Files**: `src/multiword/u256.rs` (`mul_pow10`), possibly `src/multiword/u384.rs` and `src/multiword/u512.rs` if they have similar shapes.

Replace the sequential `mul10`-loop with a `mul_u128` against a precomputed `[u128; 39]` table of `10^k` for `k ∈ 0..=38`. For `k > 38` (rare; only the very wide alignment cases), fall back to chunked multiplication: `self.mul_u128(POW10[38]).mul_pow10(k - 38)`. Adds a new `U256::mul_u128(self, other: u128) -> Self` primitive.

Affected call sites: `src/ops/addsub.rs:240, 265`, `src/ops/round.rs:114, 239`. Confirm full set with `grep mul_pow10`.

**Risk**: introducing `mul_u128` means a new primitive to test. Property test it against the existing `mul_pow10` for `k = 0..=38` over a randomized U256 sample.

**Expected**: 2–4× speedup on the alignment-heavy add/sub bench; 5-10% on the aggregate add/sub bench mix.

### 3b. Cache `decimal_digit_count` in `round_and_pack_finite`

**Files**: `src/ops/round.rs::round_and_pack_finite`.

Currently calls `coef.decimal_digit_count()` 3+ times per result (entry, post-rounding overflow check, quantum alignment). Compute once, update incrementally where the coefficient changes (only the +1 round-up that might bump digit count crossing a `10^k` boundary). The pad-with-trailing-zeros and strip-trailing-zeros branches can use the same cached count.

**Risk**: must keep the cached value correct after the +1 round-up that crosses `10^k`. Property-test against the un-cached version on randomized inputs to confirm bit-equivalence.

**Expected**: 5–15% speedup on every arithmetic op (rounding pipeline is on every call).

### 3c. Early-exit in `U256::div_rem_u128`

**Files**: `src/multiword/u256.rs::div_rem_u128`.

The bit-by-bit long division runs 256 iterations whenever `self.hi != 0`. For divisor `< 2^113` (always true since `cb < 10^34 < 2^113`), the running remainder collapses into `u128` after fewer iterations. Switch to native `u128 / u128` once `running_remainder < (u128::MAX / 2)` and the upper bits of `self` are exhausted.

**Risk**: changes division semantics — must be bit-exact equivalent. Property test against the existing implementation over randomized U256 numerators with u128 divisors.

**Expected**: 2× speedup on the magnitude-extreme division bench.

### 3d. `#[inline]` on small frequently-called helpers

**Files**: `src/bid.rs::classify_bits`, `src/bid.rs::pack_finite`, `src/bid.rs::pack_quiet_nan` / `pack_signaling_nan`, `src/bid.rs::decimal_digit_count`, `src/bid.rs::pow10`, others identified by exploration.

Add `#[inline]` (NOT `#[inline(always)]` — let LLVM make the call). These are tiny functions called multiple times per arithmetic op.

**Risk**: minimal. If LLVM was already inlining via PGO heuristics, no change. If not, modest improvement.

**Expected**: 1-3% on the aggregate per-op average.

### 3e. Make `pow10` use the same precomputed table from 3a

**Files**: `src/bid.rs::pow10`, `src/ops/addsub.rs:206, 354, 450`.

`pow10` currently is `10u128.pow(k)` which compiles to a runtime loop. The precomputed `POW10[k]` table from candidate 3a is the same data; expose it for non-multiword consumers and rewrite `pow10` as a table lookup. The "is_pow10" check in `sub_ulp_effective_sub` and similar comparison paths benefit similarly.

**Risk**: have to verify the table values against `10u128.pow(k)` for `k = 0..=38`. Add a `#[test]` that checks all 39 entries.

**Expected**: 5–15% on the sub-ULP path (used in `sub_ulp_effective_sub`).

### 3f. Unify the two sticky-bit digit-extraction loops in `round_and_pack_finite`

**Files**: `src/ops/round.rs::drop_excess_digits`, `src/ops/round.rs::shift_right_decimal` (or whichever helpers the exploration named).

Both functions iterate over digits doing similar work (`div_rem10` to extract each digit, accumulating sticky). Unify into a single helper that returns `(kept, round_digit, sticky)` in one pass, used by both call sites.

**Risk**: refactor + thorough property testing. The behavior differences between the two existing loops (if any) need to be preserved or explicitly fixed.

**Expected**: 1-3% on the aggregate per-op average.

## Phase 4 — re-bench + ship

After all six candidates land (or get reverted for null result):

1. Final bench run, captured into `ADR-0008-perf-results.md` with deltas-from-baseline.
2. README.md's Performance section updated to reflect the new numbers (replacing the 2024 figures from 1.3.0).
3. CHANGELOG entry under `[1.11.0]` listing the candidates that shipped, with measured deltas.
4. Version bump 1.10.1 → 1.11.0 (minor — no public API change but headline-worthy improvement).
5. Standard commit / push / publish / tag / GitHub release flow.

If aggregate speedup across the bench suite is < 5%, re-frame the release as a `1.10.2` patch with the bench expansions only and the optimizations as opt-in (e.g. behind a `perf-tables` feature). The published 1.10.1 is correct; we don't need to ship a worse-shaped 1.11.0 just because we promised a perf release.

- Targeted bench delta — must be ≥ 0 (no regression). Strict equality acceptable; negative reverts the commit.

For the final ship:
- All of the above plus `cargo bench --bench core_ops` showing aggregate add/sub/mul/div/sqrt/fma improvement vs baseline.
- README's Performance section numbers match the post-pass results.
- ADR-0008 records the per-bench delta with the host CPU and toolchain.

## What success looks like

**Narrow win**: 5-10% aggregate speedup across the core_ops bench suite, mostly from candidates 3a + 3b. Bench expansions ship even if optimizations don't, so future perf work has a calibrated baseline.

**Wide win**: 15-25% aggregate speedup. The README's "800 ns per add" headline drops noticeably; the ADR records the wins concretely so the next perf-aware reviewer has data to build on.

**Null win**: candidates produce no measurable change. Land bench expansions + ADR baseline + ADR documenting "perf candidates measured neutral; here's the data" as a 1.10.2 patch. Honest record beats wishful release notes.

**Beyond the perf pass**: the ADR infrastructure stays. Future decisions (whether perf-related or not) drop into `docs/decisions/` as standard practice, and approved plans archive alongside. The audit-log mechanism is the durable contribution; the perf delta is the immediate win.
