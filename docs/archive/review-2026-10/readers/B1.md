#### B1-1: the BID bit layout is not IEEE 754 BID

IEEE 754-2019 §3.5.2 (binary significand encoding): if G0G1 is not `11`, the biased exponent is G0..G(w+1) and the significand is G(w+2) through the end. For decimal128, w = 12, so the exponent is the 14 bits after the sign (bits 126..113). The free proxy is Wikipedia "Decimal128 floating-point format": "If the 2 bits after the sign bit are "00", "01", or "10", then the exponent field consists of the 14 bits following the sign bit, and the significand is the remaining 113 bits", with the table row `00xxxxxxxxxxxxccc` (exponent then `ccc`). The crate's layout (src/bid.rs:3-24, pack at :166-176) puts `T[4..3]` = exponent high bits, `T[2..0]` = coefficient bits 112..110, then the 12 bit exponent continuation at 121..110. That is the DPD combination field structure with a binary coefficient.

Reproducer `{{SCRATCH}}/B1/bits/` (`cargo run --release -q`, expected values computed from §3.5.2):
```
d128 1E0: crate 22080000000000000000000000000001  ieee 30400000000000000000000000000001  DIFFER
      crate decodes the IEEE pattern as Some(Decimal128Parts { negative: false, coefficient: 5192296858534827628530496329220097, exponent: -1824 })
d128 1E1: crate 22084000000000000000000000000001  ieee 30420000000000000000000000000001  DIFFER
d128 123E-2: crate 2207800000000000000000000000007B  ieee 303C000000000000000000000000007B  DIFFER
d128 1E-6176: … same
d128 9999999999999999999999999999999999E6111: … same
d64 1E0: crate 2238000000000001 ieee 31C0000000000001
d32 1E0: crate 22500001 ieee 32800001
```
`0x3040…01` (d128 one), `0x31C0000000000001` (d64 one) and `0x32800001` (d32 one) are the well known BID encodings. The patterns agree only where the middle exponent bits happen to match the coefficient MSBs (exponent 0 or all ones). The specials (Inf `0x78…`, NaN `0x7C…`, sNaN `0x7E…`) agree in both layouts.

Impact: `to_bits` is documented as "the raw 128-bit BID encoding". The README says the crate "implements the BID 128 … format from IEEE 754:2019" and offers `ferrodec::serde_bid` for "raw 128-bit BID serialization". Any exchange with another IEEE BID implementation (Intel's library, GCC `_Decimal128` on x86, database BID columns) silently reads wrong values: an IEEE `1` decodes as `5.19…E-1791`. Arithmetic, string I/O and the DPD codec are internally consistent and unaffected (DPD goes through decoded parts and passes dqEncode). The sibling layouts (`ferrodec-decimal64/src/bid.rs:3-24`, and d32 by the same reproducer) belong to B2's files; the reproducer above covers them.

Why the stack missed it: every BID instrument is self consistent (trust table rows "strings, from_bits, canonical, dpd, decode, serde, roundtrip": "round trips … self-consistency … parse/format pairs that agree on a wrong form"; Kani root "BID/DPD round trips" proves the crate's encode and decode inverse to each other, not to the standard). The only external bit pins are `infinity_bit_patterns_match_intel_reference` (src/decimal.rs:293), which covers exactly the four specials, the patterns both layouts share. Every finite bit literal in the tests (tests/regression_fd_7nf.rs:77, the proptest regression seeds) was produced by the crate itself. PLAN.md:266-271 planned Intel BID vectors as Tier 3, but they were never vendored. dqEncode is DPD, so it cannot see this. June found "codecs clean" with the same blind spot.

#### B1-2: spurious OVERFLOW from `fma` at the `10^(Emax+1)` binade

Command: `{{SCRATCH}}/target-B1/release/b1drv < {{SCRATCH}}/B1/repro_B1-2.txt`, with the same file through `orc`:
```
input                                                    b1drv (ferrodec)                                 orc (oracle.rs)
fma tz F,0,1,6100 F,0,1,45 F,1,1,6000                   F,0,9999…9999,6111 20  (INEXACT|OVERFLOW)         F,0,9999…9999,6111 16 (INEXACT)
fma tn F,0,1,6100 F,0,1,45 F,1,1,6000                   … 20                                             … 16
fma tz F,1,1,6100 F,0,1,45 F,0,1,6000                   F,1,…,6111 20                                    F,1,…,6111 16
fma tp F,1,1,6100 F,0,1,45 F,0,1,6000                   F,1,…,6111 20                                    F,1,…,6111 16
fma tz F,0,1E17,6111 F,0,1E17,0 F,1,1,-6176             … 20                                             … 16
```
libmpdec (`clamp=1`) agrees with oracle.rs (16). Rational check (`/usr/bin/python3`, Fraction): `10^6145 − 10^6000 > MAX` and `< MAX + 10^6111`. Rounding toward zero with an unbounded exponent gives `MAX`, which does not exceed the largest finite number, so §7.4 raises no overflow. The family run (`py/emax.py`, 19,080 cases) produced 1,260 mismatches. All of them are this flag only (tz 630, tn 315, tp 315), and every one has a product exactly `10^6145` and an addend gap of at least 77 decades (the `ab_too_wide` regime). Gaps of 76 or less go through the in buffer path and are clean.

Trace: `fma_finite_kernel` (fma.rs:321) finds `ab_too_wide` and calls `fma_sub_ulp` (fma.rs:435). There `cab_top_exp = cab_digits + qab − 1 = 6145 > E_MAX` (fma.rs:515-516) leads to `sub_ulp_round(cab, …)`, which rounds `10^6145` (plus a positive sticky) into `round_and_pack_finite`'s overflow disposition, so the caller gets `overflow_result` (MAX under TZ) with OVERFLOW set. The comment at fma.rs:491-494 ("a sub-ULP residue can't pull magnitude back across `MAX − 0`") is false at exactly this point: `10^6145 − ε` lies strictly between `MAX` and `MAX + ulp`. This is a sibling of P1B-3 (the same "power of ten minus ε, rounded toward zero" class) at a different line, with a different observable (flag, not value). P1B-3's proposed closure at fma.rs:791-804 does not reach it.

Why the stack missed it: property_fma_oracle draws uniform coefficients and exponents. A product landing exactly on `10^(Emax+1)` with a far opposite sign addend under a directed mode has negligible probability (trust table row "property_fma_oracle ×3 … blind spot: the C2-1 shape"). dqFMA has no such row, and Kani is special value only.

#### B1-3: `scaleb` uses a GDA range gate in an IEEE operation

`repro_B1-3.txt` through `b1drv`: `scaleb ne 1 12357` gives `Q,0,0 1` (NaN, INVALID). `scaleb ne Infinity 12357` gives `Q,0,0 1`. `scaleb tz 1 2147483647` gives `Q,0,0 1`. Under IEEE 754-2019 §5.3.3, scaleB is the exact `x·10^N` rounded to the destination, so the expected results are `+∞` (OVERFLOW\|INEXACT) under NE, `MAX` (OVERFLOW\|INEXACT) under TZ, and `∞` exactly for an infinite x. The code (quantum.rs:204-213) states the gate comes from GDA and libdfp, and the rustdoc (quantum.rs:180-182) documents it. But the method is headed "IEEE 754-2019 §5.3.2 `scaleB`" (the section is wrong too: §5.3.2 holds quantize/quantum, §5.3.3 holds scaleB/logB). This is a documented divergence, not a hidden one; I report it because the method's contract names the IEEE operation. The GDA behaviour belongs to `ferrodec-decimal` (ADR-0041). The libmpdec sweep agreed with the crate (30,000 cases) because libmpdec implements the same GDA gate. That is the blind spot: the oracle and the code share the GDA reading.

Why the stack missed it: conformance comes from dqScaleB (GDA), which encodes the gate, and the oracle does not model scaleb.

#### B1-4: non canonical NaN payloads survive arithmetic and order by raw bits

`repro_B1-4.txt`: `add ne Q,0,10^33 F,0,1,0` gives `Q,0,1000000000000000000000000000000000 0` (still non canonical). `canon` of the same NaN gives `Q,0,0`. `totcmp Q,0,10^33 Q,0,1` gives `Greater`, while `totcmp Q,0,0 Q,0,1` gives `Less`. `nan_from` (nan_propagate.rs:21-27) copies `bits & T_MASK` unchanged, and `signed_payload_cmp` (cmp.rs:127) compares raw payloads. The crate's own `canonicalize` (classify.rs:~393-405) and `MAX_CANONICAL_NAN_PAYLOAD` treat such a payload as 0. Reaching this state requires `from_bits` with a non canonical NaN; June's finding closed the `parse_str` route. P2 because the inconsistency is internal and the IEEE requirement that computational results be canonical is one I could not quote verbatim (see Least sure).

#### B1-5: abs_with_status and neg_with_status mislabelled as §5.5.1

Behaviour (b1drv, abs sweep, 823 rows): `abs ne S,1,5` gives `Q,1,5 INVALID`, and `abs ne Q,1,0` keeps the sign. This matches GDA `abs` (libmpdec `Context.abs` agrees once the reference uses it). The rustdoc at classify.rs:220 ("IEEE 754 §5.5.1 compliant absolute value: raises `INVALID` for signaling-NaN inputs") and at classify.rs:257 ("IEEE 754 §5.5.1 compliant negation") contradicts §5.5.1, whose sign bit operations are quiet computational, signal no exception, and only affect the sign bit (so `negate(+0)` is `−0`, while `neg_with_status(+0)` returns `+0`). Documentation only.

#### B1-6: `TEN` unpinned by value

`grep -rnw Decimal128::TEN src tests`: classify.rs:449, :841, :921, :1052 and decimal.rs:257 are predicate, signum and distinctness uses. None reads `(10, 0)`. Every other public constant is pinned by `decode()` or a bit literal (see the pin table).

### Design notes

1. **The bit layout should live in one place, with an external witness.** The three `bid.rs` files each transcribe the same DPD-shaped combination split (B1-1). A shared `ferrodec-ieee` layout module, parameterised by w and t and pinned by a handful of §3.5.2 literals per format, would have caught the defect once. Evidence that would make this a finding: B2 confirming that the d64 and d32 layouts carry the same transcription.
2. **min/max claim 2008 `minNum` semantics in a 2019 crate.** IEEE 754-2019 replaced minNum/maxNum with `minimum`/`maximum` and `minimumNumber`/`maximumNumber`. The root documents the GDA/2008 behaviour honestly (cmp.rs:175). A 2019 conformant pair would differ on sNaN and on ±0. This becomes a finding if any doc claims §9.6 2019 conformance for these methods.
3. **Regime gates in fma are proven only by comment.** `fma_sub_ulp` (fma.rs:423-540) chooses among four regimes on `cab_top_exp`, `BUFFER_DIGIT_LIMIT` and sign. Both known defects (P1B-3, B1-2) sit where a gate's comment asserts "cannot cross", and the exact power of ten edge breaks that claim. A property strategy with a power of ten or all nines product at every gate edge (gap ∈ {76, 77, 110, 111}, product ∈ {10^k, 10^(Emax+1)}) is cheap insurance.
4. **GDA and IEEE mixing on the root's public surface.** scaleb (B1-3), abs/neg_with_status (B1-5), min/max (note 2) and divide_integer and rem's Division_impossible are GDA behaviours under IEEE section headings. One table in `docs/` listing which root methods follow GDA where IEEE differs would turn each from a surprise into a decision.
5. **`round_and_pack_finite`'s `unwrap_or(u32::MAX)` then `as i32`** (round.rs:79/87) is a total function only because its callers are well behaved. Taking the exponent as a newtype bounded to the caller range, or saturating at a value that keeps `excess as i32` positive, would make the bound local.
