#### B4-1 power: exact and midpoint results with a non-integer exponent

Evidence (`run_repros.sh`, oracle: exact arithmetic, the true values are `2` and `1.25`; libmpdec agrees: `2.00000000` in every mode, `1.3` for HalfUp):

```
pow(4,0.5) p9 Down: 1.99999999 [Status(16)] elapsed=2.473s
pow(4,0.5) p9 Floor: 1.99999999 [Status(16)] elapsed=2.465s
pow(4,0.5) p9 ZeroFiveUp: 1.99999999 [Status(16)] elapsed=2.475s
pow(4,0.5) p9 HalfEven: 2.00000000 [Status(16)] elapsed=178.375µs
pow(1.5625,0.5) p2 HalfUp: 1.2 [Status(16)] elapsed=3.259s
```

Also `pow(9,0.5)` Down/Floor/05up = `2.99999999`; p=34 and p=100 Down give `1.999...9` (2.5 s each). Trace: `power` (pow.rs:68) → `integer_kind` NonInteger → `general_power` (pow.rs:187) has no exactness test → `finish` (strategy.rs:73): the bracket `[v-4, v+5]` straddles the exact value `2`, so under Down the low end rounds to `1.99999999` and the high end to `2.00000000` at every guard; under HalfUp the bracket straddles the tie `1.25`. After 11 doublings `faithful_round` (strategy.rs:123) rounds `v`, which sits below the exact value. Contract violated: lib.rs:20-23 and the README say `power` "is correctly rounded with the context's rounding mode, stronger than the reference".

Why the stack missed it: `tests/pow_oracle.rs` computes the oracle by calling the same `power` at a wider precision (same Ziv path, same cap, same fallback), so it is not independent on exactly these inputs, and its sample (`2^0.5`, `10^2.5`, ...) has no perfect power; `property_pow.rs` draws random non-integer exponents (no exact results); the conformance runner and the differential compare `power` within a one-ulp band that would accept `1.99999999` against `2.00000000` (B4-12). The C2 trust table's "power band" row is the instrument; its blind spot is precisely exact results.

#### B4-4 Ziv cap: reachability, cost, distinguishability (dossier)

(a) Reachability. `exp`, `ln`, `log10` round half even only, so the cap needs a true value within `~10^-(p+16384)` of a midpoint. Their exact detection is complete for rational inputs (exp: only `x = 0`; ln: only `x = 1`; log10: exact powers of ten; any other rational input has a transcendental result, never exact or a midpoint). The cap is still reachable with a crafted operand: `x = ln(1.000000005)` to 20,000 digits (mpmath, dps 20100). Evidence:

```
exp(crafted 20000-digit x) p9: 1.00000000 [Status(16)] elapsed=1.697s
ln(crafted 20000-digit y) p9: 1.00000000 [Status(16)] elapsed=2.196s
mpmath dps 40200: exp(x) - 1.000000005 = 2.4261e-20009 ; ln(y) - 1.000000005 = 1.5527e-20000
```

Both true values sit above the midpoint, so the correct half-even result is `1.00000001`; the crate returns `1.00000000`. For `power`, the cap is reachable by trivial inputs (B4-1, B4-2, B4-3).

(b) Exact detection misses (power only): non-integer exponents with exact or midpoint results (perfect powers `a^n` raised to `1/n` written as a decimal: 0.5, 0.25, 0.2, 1.5, ...); integer exponents with `base_digits * n > 20000` (powers of ten, `±1`, and at large precision any `x^n` that fits); and the `-1` base. `pow(x,0)` (pow.rs:93), `pow(x,1)` and `pow(10,2)`, `pow(2,10)` take exact paths and are correct.

(c) Cost. `MAX_DOUBLINGS = 11` with `INITIAL_GUARD = 8`: 12 kernel runs at guards 8, 16, ..., 16384, so the cap is bounded, not "astronomically wide". Measured wall time at the cap: 0.48 s (`pow(-1,1e5)`, trivial kernels), 1.7 to 2.5 s (p = 9, 34, 100), 3.0 s (p = 1000), 6.6 s (p = 5000); decided calls take 0.2 ms (p=9), 9.7 ms (p=1000), 187 ms (p=5000). Amplification about 10^4 at small p. An attacker who controls only operands at a fixed small precision gets about 2.5 s per call, not minutes; minutes require a caller-chosen precision in the tens of thousands (not probed). The final kernel at guard 16384 dominates.

(d) Distinguishability: none. Every result above carries `Status(16)` (INEXACT only), identical to a decided result; the signature is `(Decimal, Status)` with no other channel.

Why the stack missed it: the transcendental differential and `property_exp/ln` draw random operands (my own 10,843 random cases at p = 7 to 10,000 were also all correct); ADR-0040 priced the cap by probability, which does not bind adversarial or structured operands.

Evidence (`run_repros.sh`; oracle: arithmetic, e.g. `1E-2147483648 * 0.1 = 1E-2147483649`, which the `i32` exponent cannot hold):

```
1E-2147483648 * 0.1 (p9, emin i32::MIN): 1E+2147483647 [Status(0)]
1E-2147483648 / 10 (p9, emin i32::MIN): 1E+2147483647 [Status(0)]

sqrt(2) pU32MAX: 1 [Status(24)]
1/3 pU32MAX: 0 [Status(24)]
exp(2) at p = 4294967290: a 16,379 digit value [Status(16)] in 1.8 s (wp = p + 8 wrapped to 2)
```

Sites: round.rs:43 (`etop`), :56, :120, :159, :171 (`as i32`); next.rs:177, :184 (`precision as i32`, `i32` subtraction); divrem.rs:74 (`shift as u32`, shift = p+1 = 2^32 wraps to 0); sqrt.rs:76 (`twos as u32`); strategy.rs:79 (`precision + guard`); pow.rs:210-211; ln.rs:125, :138. Why missed: the only extreme-context tests (arith.rs:399, :422) use results that overflow or fold into sticky; no test multiplies or divides into the region below `i32::MIN`, and no test uses a precision above 2^31.

#### B4-10 clamp=1 ignored by quantize, reduce, divide_integer

#### B4-14 NaN payload under clamp

All `nanpayload` mismatches in the differential (about 100 per 60k cases) have `clamp=1` (zero with clamp 0): libmpdec keeps `precision - 1` payload digits (the IEEE interchange capacity) where `quiet_from` (arith.rs:325-329) keeps `precision`. Reproduced against libmpdec only; I did not check whether the GDA text mandates `precision - clamp`.

### Least sure

- GDA completeness claim (lib.rs:17-27, "the whole General Decimal Arithmetic specification"): `Status` has no Rounded, Subnormal or Lost_digits, and collapses Division_impossible, Division_undefined, Conversion_syntax and Invalid_context into INVALID; the conformance runner documents ignoring them, but no ADR I read records the omission against the completeness claim. Possibly P3.
- `parse_str` rejects exponents beyond `i32` (convert/parse.rs:164) where GDA to-number would round to Infinity/0 with Overflow/Underflow; 16 base.decTest and 23 quantize.decTest rows are skipped for it. The skip reason is true; whether this is an acceptable bound is a design call.
- The 99 skips by class, reasons checked against code today: 31 fixed-format `#` literals (true; unrepresentable), 18 `Invalid_context` (true: they are decNumber limits; I ran powx1183/1184 `7 ** 1e9` and the crate returns the mpmath-correct `1.03337234E+845098040` in 0.27 ms), 4 `DEC_MAX_MATH` power rows (true), 39 exponent beyond `i32` (true), 7 `rescale` rows skipped by the runner's catch-all `_ => Skip` (conformance.rs:450; `rescale` is not a current GDA operation, but the catch-all would also hide a misspelt operation silently).
- Cost at very high caller-chosen precision (p ≥ 20,000) at the Ziv cap was not measured; extrapolating 3.0 s (p=1000) and 6.6 s (p=5000) suggests tens of seconds, not verified.
- `multiply`/`divide` compute the full product/quotient of arbitrarily long operands before rounding (arith.rs:52); cost is O(n·m) in operand length regardless of precision. libmpdec does the same; I did not time 10^6 digit operands.
- `rounded_one` (pow.rs:301) under clamp=1 and `far_underflow` exponents near `i32::MIN` (pow.rs:289 `etiny as i32`) belong to the B4-5 class; not separately reproduced.
- `DecBig::from_ascii_digits` panics on a non-digit byte (multiword, B5's file); the crate's only caller (parse.rs) feeds digits only, so not reachable through this crate.

### Found clean

- `DecBig` normal form as used by this crate (checklist 1): every constructor goes through `from_limbs`, which strips high zero limbs; `from_ascii_digits` validates unconditionally since fd-aqs.14; no public path in `ferrodec-decimal` builds a non-normal value. Method: read. Blind spot: B5 owns the multiword internals.
- Arithmetic differential against libmpdec (`py/diff_arith.py`, structured operands: zeros at every exponent, `10^k`, `9…9`, `5·10^k`, `4…9`, `9…95`, `10…01`, near Etiny and Nmax, specials with payloads; precisions 1, 2, 3, 4, 5, 7, 9, 16, 34; emax from p+2 to 6144; all 8 modes; clamp 0 and 1): 270,000 cases, roughly 11,000 per operation for add, subtract, multiply, divide, divide_int, remainder, remainder_near, quantize, max, min, compare, next_toward, scaleb, plus, minus, sqrt, next_plus, next_minus, to_integral_value/exact, normalize, logb, and about 32,000 fma. Zero mismatches outside the B4-9, B4-10 and B4-14 classes. Blind spot: libmpdec shares any misreading of GDA; no `power`; operand exponents stay small relative to `i32`.
- Transcendental differential against mpmath (correct rounding derived from mpmath at dps p+60, cases within 10^-40 of a boundary excluded, none occurred): 10,843 random cases, `exp`/`ln`/`log10` half even and `power` in all 8 modes, at p = 7, 16, 34 (10,200), 100 (600), 1000 (40), 10,000 (3); zero mismatches. Deepest precision exercised: 10,000 (three cases in 1.27 s total); about 0.08 ms per call at p ≤ 34 and about 6.5 ms per call at p = 1000. Blind spot: random operands never produce exact results or midpoints (B4-1 to B4-4).
- decTest replay (instrumented copy): 27,494 pass, 0 fail, 99 skip, matching the pinned counts. Blind spot: the power band (B4-12).
- ADR-0053 guards in add, subtract, fma, quantize, remainder, remainder_near, divide_integer, compare (table above). Method: probes at gaps near 2·10^9 with RSS measurement, values checked against libmpdec.
- `round.rs` rounding core for in-range contexts (Etiny single rounding, tininess before rounding, overflow per mode including `ZeroFiveUp` to Nmax, zero exponent tidying): read plus the differential.
- `from_float.rs`: exact by construction; read.
- `exp`/`ln`/`log10` exact-case detection is complete for rational operands (argument in B4-4 (a)).

### Design notes

1. `Context` should be a validated type (private fields, constructor returning `Option`), so that precision ≤ a ceiling and `emin - (p-1)`, `emax - (p-1)` fit `i32`; evidence: B4-5 and B4-6 are one missing invariant expressed at a dozen call sites.
2. `Work` lets a zero carry `sticky` (work.rs:143-147, :198-204); a sticky bit has meaning only relative to a digit position, so a "sticky zero" should either be unrepresentable or carry its exponent window; evidence: B4-3's `2`.
3. The Ziv entry point should return a tri-state (decided, decided exact, cap reached) and let the public operation decide what to report; evidence: B4-4 (d).
4. `power`'s exactness should be decided on the mathematical result (exact root or exact power test on the coefficient) rather than on input size caps; evidence: B4-1, B4-2, B4-11 come from the same `EXACT_DIGIT_CAP` and the absent root test.
5. The interop and `to_f64` bridges ride `Display` plus `parse`; a direct coefficient/exponent bridge would make the NaN payload and flag rules explicit; evidence: B4-7, B4-8.
