### D1-1: `serde` silently requires an allocator

Reproducer (`$SCRATCH/D1/noalloc`, `noalloc_feat`, `noalloc_ctl`): a `#![no_std] #![no_main]` thumbv6m binary with a hand written minimal `Serializer`, `panic = "abort"`, no `#[global_allocator]`.

```
noalloc (ferrodec features fmt,serde; _start calls Decimal128::ONE.serialize):
error: no global memory allocator found but one is required; link to std or add `#[global_allocator]` to a static item that implements the GlobalAlloc trait
noalloc_feat (features fmt,serde; _start only calls add, never serialize):
error: no global memory allocator found but one is required; ...
noalloc_ctl (features fmt; same _start as noalloc_feat):
    Finished `release` profile [optimized] target(s) in 1.69s
```

Mechanism: `src/serde_impls.rs:29` `extern crate alloc;` at module level (not under `cfg(test)`), `:31` `use alloc::string::ToString`, `:46` `let s = self.to_string();`. The sibling copies are at `ferrodec-decimal{64,32}/src/serde_impls.rs:14,16,27`. Linking the `alloc` crate into the graph is enough to demand an allocator, so the requirement attaches to the feature, not to the call. The claims it contradicts: `Cargo.toml:86` and `ferrodec-decimal64/Cargo.toml:10` (`no-std::no-alloc`), `README.md:78` ("allocates nothing on its own"), and `README.md:153`, whose serde row lists no allocator need while the `unbounded-ladder` row (`:150`) does. This is the "fact stated in prose" shape: the feature table is the specification and the type of the dependency graph disagrees. The fix shape exists in serde itself: `collect_str` is a required method on `no_std` serializers, which the probe hit (`E0046 missing collect_str`) before adding it.

Why missed: every thumbv6m lane (ci.yml:72-77, gate_battery.sh lane_thumbv6m, my matrix) builds an rlib, and an rlib never resolves the allocator symbol; only a final link does. No lane links a binary.

### D1-4: the `DecimalFormat` seam

Reproducer `$SCRATCH/D1/seam` (calls `<F as DecimalFormat>::nan_from(F::ONE)` for each format):

```
-- debug
thread 'main' panicked at /Users/parnell/Development/ferrodec/src/ops/nan_propagate.rs:22:5:
Decimal128: nan_from(1) panicked
Decimal64: nan_from(1) = NaN
Decimal32: nan_from(1) = NaN
-- release
Decimal128: nan_from(1) = NaN1
Decimal64: nan_from(1) = NaN
Decimal32: nan_from(1) = NaN
```

The trait is `pub` and re-exported (`lib.rs:163`), each format implements it publicly, and `format.rs:93-95` states the precondition in prose ("Caller guarantees `self.is_nan()`"). Root `nan_propagate.rs:21-27` guards with `debug_assert!` and in release packs the finite coefficient as a payload; the siblings' `quiet_nan_of` (`ferrodec-decimal64/src/transcend_impl.rs:63-75`) falls back to `Self::NAN`. I propose P2 rather than P0: the panic is a `debug_assert` on a documented precondition, release does not panic, and no in tree caller violates it; the coordinator may rule otherwise under the "panic reachable from the public API" letter.

`round_and_pack_finite`'s `status`: the trait doc says the forward honours "the accumulated `status`" (format.rs:118-122). `grep F::round_and_pack_finite` gives 17 call sites in `extended.rs`, `extended2.rs`, `exact.rs`, `exact_pi.rs`, `exp.rs`, `hyperbolic.rs`, `hypot.rs`, `extended_dyn.rs`, every one passing `Status::OK`; root forwards it (`src/math/format_impl.rs:103-111`), both siblings discard it (`let _ = status;` at `ferrodec-decimal{64,32}/src/transcend_impl.rs:185`). A dead parameter whose meaning already differs between impls.

The trait carries `BIAS` and `PRECISION` but no `E_MAX`/`E_MIN`, so the two `exp` gates are per impl hand literals with prose derivations (`14150/14221`, `887/918`, `224/235`) rather than a table derived from the format's range; that is the structure behind A5-1/A5-2's borrowed gates (A5 design note 2). The doc's "three generic boundaries" (format.rs:20-42) omits `div_fmt`, `mul_fmt`, `to_i32_fmt` and the gates, which are full arithmetic, not the "loop free and cheap" members the paragraph describes. `mock_format.rs` is faithful only for `classify`, `to_extended_parts`, `PRECISION`, `BIAS` (every other member is `unreachable!()`), which is C1-11's finding and is honestly documented at mock_format.rs:1-7 and :17-27; its `MockFmt<const P: u32, const B: i32>` is the one existing const generic instantiation of the seam.

## Design notes

1. **Make the gate table a derivation, not a literal.** The seam lacks `E_MAX`/`E_MIN` (format.rs:46-48), so each impl hand writes two integers with a prose derivation. Two associated consts and a `const fn` that computes `⌈(E_MAX+1)·ln 10⌉`-style bounds from an Extended `ln 10` would make A5-1/A5-2's class unrepresentable. Evidence that would make it a finding: a gate literal below its derived value (B2's gate table says the siblings must supply at least 887.19 and 224.05).
2. **Seal the seam and narrow the crate.** `DecimalFormat` plus 69 public kernels plus a public `Extended` with public fields is a published API surface whose only consumers are three sibling crates and one unpublished campaign crate. A sealed trait, private fields, and a `campaign` feature for the research entry points would let the crate change kernels without majors. Evidence: the next `DecimalFormat` method addition (any gate or seed fix in the open P0s) is a breaking change for `ferrodec-transcend` today.
3. **Public dependencies are part of the semver surface.** `ferrodec-decimal` re-exports `DecBig` and takes it in `finite`/`quiet_nan`/`signaling_nan` (lib.rs:85, decimal.rs:55-87), so `ferrodec-multiword` 0.2 is in its API; `impl DecimalFormat for Decimal128` puts `ferrodec-transcend` 0.3 in ferrodec's. A `DecBig` major forces a `ferrodec-decimal` major. Evidence: a `cargo semver-checks` run across a multiword bump.
4. **Namespace the test cfgs.** `ferrodec_force_escalate` etc. would prevent a dependent's identically named cfg from arming `ladder_audit`'s panics in shipped code. Low cost, no behaviour change.
5. **The seed boundary should not round trip through the format.** `recip_seed`/`sqrt_seed` return `(Self, Status)`, a type that cannot express "the seed lies outside the format's range", which is the structure behind the Newton seed P0 class (fd-0o9, fd-h3jk): the type forces a format value, and `from_format` then panics on the infinity. A seed returned as `Extended` (or `Option<Self>`) makes the panic class untypeable.

- **What a generic `Decimal<const P, const EMAX>` would need from the current code** (stable Rust, MSRV 1.84, no `generic_const_exprs`):
  - a storage type chosen per format (`u32`/`u64`/`u128`) and wide intermediates (d32 u64/u128, d64 u128, root `U256`/`U384`): const generics cannot select a type, so the parameter has to be a trait with associated types (`trait Format { type Bits; type Wide; const P; const E_MAX; }`), which is what `DecimalFormat` already half is;
  - array lengths derived from `P` or the width: `[u8; PRECISION]` digit buffers (`digits.rs`), `to_dpd_bytes -> [u8; 16|8|4]`, the `POW10_*` tables: each needs an associated array type or a const expression stable Rust does not allow in that position;
  - signatures whose shape follows from exactness (`from_i32`/`from_i64` return `D` or `(D, Status)`; `From<i64>` only where exact; `try_new` integer width): a generic either unifies them on the rounding form (an API break on root and d64) or keeps per instantiation impls, which concrete impls on `Decimal<34, 6144>` allow;
  - already present: the kernel seam (`DecimalFormat` with `PRECISION`, `BIAS`), the shared `ferrodec-ieee` types, and `MockFmt<const P: u32, const B: i32>` (mock_format.rs) proving the predicates instantiate at synthetic shapes;
  - ADR-0011's own trigger (D1-7) and its "three concrete uses" precondition are both met today.
