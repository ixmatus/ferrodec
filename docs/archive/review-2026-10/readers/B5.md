#### B5-1: `inv_pi_digits` panics inside its own contract

Code path. `inv_pi_digits(n)` (bigconst.rs:479) runs `checked_digits(n)` (passes for `n <= 100_000`), sets `scale = n + GUARD` (line 481, `GUARD = 24`), and calls the public `pi_digits(u64::from(scale))` (line 482), which runs `checked_digits(scale)` again (bigconst.rs:124-129) and asserts `scale <= MAX_DIGITS`. Every other two stage generator (`two_over_pi_digits`, `inv_ln2_digits`, `inv_ln10_digits`) uses the unchecked internal `pi_at_scale` or `odd_reciprocal_series`; only `inv_pi_digits` (added in 74108bf, fd-4zo.26) goes through the checked public entry. The module contract (bigconst.rs:70-79) and the `# Panics` sections promise a panic only outside `MIN_DIGITS..=MAX_DIGITS`.

Reachability. The `minimum_digit_count_is_supported` test covers the floor for all nine generators; the ceiling has no counterpart. The trust table row "multiword tests" names multi limb width as its blind spot, not the depth contract.

#### B5-2: subnormal binary results do not raise UNDERFLOW

Code path. `Decimal128::to_f64` (src/convert/binary.rs:117-…) parses the exact decimal string into `f64`, then `binary_status` (binary.rs:44-60) calls `ferrodec_ieee::binary_conversion_status(coef, exp, inf, zero, subnormal, 53)`. Its `is_subnormal` arm (ferrodec-ieee/src/binary.rs:39-40) returns `Status::INEXACT` alone. The Decimal64 and Decimal32 `to_f64`/`to_f32` paths call the same function (ferrodec-decimal64/src/convert/binary.rs:82 and :163; ferrodec-decimal32/src/convert/binary.rs:82 and :179).

Derivation that every subnormal result is tiny and inexact. A binary64 subnormal is `odd · 2^-k` with `k >= 1023`; its exact decimal expansion has at least `k · log10 5 >= 715` significant digits, so no Decimal128 (34 digits), Decimal64 or Decimal32 value equals one; for binary32, `k >= 127` gives at least 88 digits. So every finite nonzero decimal whose conversion lands in the subnormal range is inexact (the code's "conservatively INEXACT" is in fact exact), and its value lies strictly below the smallest normal, so it is tiny under either tininess rule of §7.5. IEEE 754-2019 §7.5 default handling: a tiny result that is inexact raises the underflow flag. The function raises UNDERFLOW only when the result rounds all the way to zero.

Reproduced. `$S/B5/mw/src/bin/uf.rs` (scratch crate `$S/B5/mw`, `ferrodec` with `binary-float`):

```
$ cd $S/B5/mw && CARGO_TARGET_DIR=$S/target-B5 cargo run -q --bin uf
                    1E-310 -> f64 1e-310 Subnormal inexact=true underflow=false
                  4.9E-324 -> f64 5e-324 Subnormal inexact=true underflow=false
   2.2250738585072011E-308 -> f64 2.225073858507201e-308 Subnormal inexact=true underflow=false
                    1E-400 -> f64 0e0 Zero inexact=true underflow=true
binary_conversion_status(1, -310, subnormal) bits=0x10 underflow=false
```

Oracle: IEEE 754-2019 §7.5 (pointer only; the clause text decides) plus the digit count derivation above, which is exact integer arithmetic. The doc at binary.rs:19-25 and the `to_f64` rustdoc ("a result of ±∞ / ±0 raises OVERFLOW / UNDERFLOW") describe the implemented behaviour faithfully, so this is a spec divergence by design, not drift.

Why the stack missed it. `binary.rs` unit tests exercise only `decimal_is_binary_exact`; nothing tests `binary_conversion_status`, and the format side test `to_f64_is_correctly_rounded` checks the value, not the flags. The C2 trust table has no row for the binary conversion flags. fd-aqs.12 fixed the INEXACT half of the June finding and wrote the subnormal arm without the underflow rule.

The family is derived from TAOCP Vol 2 §4.3.1 Algorithm D: with the top divisor limb `v1 >= B/2` (so the normalisation factor is 1), take the dividend window equal to `q̂ · (v1·B + v2) · B^(n−2)` exactly, so `r̂·B + u_{j+n−2}` equals `q̂·v2` and the D3 test cannot lower `q̂`, while nonzero low divisor limbs make `q̂·v` exceed the window by `q̂·L > 0`; D4 goes negative and D6 adds back. Random operands fire the branch zero times in 683,645 quotient limbs, so the single in tree witness is the only coverage, and it has n = 3 and d = 1.

Why this is P2, not a correctness finding. The branch is correct on everything I threw at it. The defect is in the instrument: the test asserts `q`, `r`, and the division identity, which a branchless correct path would also satisfy, so a refactor that stopped reaching D6 (for example a different D3 test) would leave the test green while the branch went back to zero coverage. The fixed width types carry no Algorithm D at all (see Found clean), so there is nothing to cover for `U256`, `U512`, `U1024`.

#### B5-4: `U256::isqrt` partial at 255 and 256 bits

Code path. `isqrt` (u256.rs:243-294) seeds `x = 1u128 << half_bits` with `half_bits = ceil(bit_len/2)`; for `bit_len` 255 or 256 that is `1 << 128`, guarded only by `debug_assert!(half_bits <= 127)` (lines 267-271). Every `U256` is below `2^256`, so its floor root is below `2^128` and fits `u128`; the restriction exists only because of the seed. The message and comment say the cap exists "so the result fits in u128", which is false for these inputs (`floor(sqrt(2^255)) ≈ 2.4e38 < 2^128`). The doc's "We assert that here" is a debug assert.

#### B5-7: CLAMPED attributed to IEEE 754-2019 §7.4

status.rs:21 reads "(IEEE 754-2019 §7.4, informational)" and status.rs:14 says the flags "follow IEEE 754-2019 §7". §7 of IEEE 754-2019 defines five exceptions (7.2 invalid operation, 7.3 division by zero, 7.4 overflow, 7.5 underflow, 7.6 inexact); clamping is the General Decimal Arithmetic specification's Clamped condition, which ADR-0048 already treats as decNumber derived. The text is generated into `docs/references/registry-status-flags.md:36` from `ferrodec-test-support/tests/references_integrity.rs:137`, and the registry's own prose (line 27) says "The six IEEE 754-2019 §7 flags". Confidence is traced, not reproduced: the standard is pointer only here, and I am citing its clause structure from the free proxy literature and the GDA text, not from a copy.

There is no `Display`, no `contains`, no `&`, so no set semantics beyond union are claimed. Consumers that rely on numeric bit values: ferrodec-campaign/src/sample.rs:391-395 prints `bits()` in hex into campaign output, and references_integrity.rs pins the bit positions into the registry, so the values are de facto frozen and pinned. No consumer depends on an ordering.
- **`classify.rs`, `digits.rs`**: no tables or thresholds in this crate (the per format thresholds live in the format crates). `IeeeClass` has the ten §5.7.2 classes. `decimal_digit_count_u128` is pinned at every `10^k` and `10^k − 1` and at `u128::MAX`.

Allocation only in `decbig`/`bigconst` behind `alloc`. No `const fn` that can panic in const evaluation apart from `U256::to_u128`'s debug assert. ### Design notes

1. **One generator entry, one contract check.** B5-1 exists because the public, checked `*_digits` functions double as building blocks. Splitting each into an unchecked `*_at_scale` core and a thin checked wrapper (the shape `pi_at_scale` already has) would make "every internal depth is unchecked" a structural fact. Evidence that would make it a finding: a second generator composed from a checked public one.
2. **`mul_pow10` across widths.** `U256` panics in release past k = 76 (an explicit `assert!`); `U384`, `U512`, `U768`, `U1024` wrap silently past capacity with only a per step debug assert. A shared contract (all assert, or all documented as wrapping) would match the crate's stated "release trusts the caller" posture. Evidence for a finding: a caller whose envelope argument for a `U384`+ `mul_pow10` fails.
3. **`decimal_is_binary_exact`'s `mantissa_bits: u32`** admits values where the arithmetic overflows (B5-5). A `BinaryFormat { F32, F64 }` parameter makes the precondition unrepresentable at no cost; the two callers pass literals.
4. **Five copies of `div_rem_u128_with_carry_in_by_10`** (u384.rs:295, u512.rs:253, u768.rs:235, u1024.rs:242, and the inlined U256 form) are deliberate per the module comments; a single `pub(crate)` helper would halve the review surface. Evidence for a finding: a divergence between copies (none found; the differential exercised all five).
5. **Make the add back branch observable.** A `cfg(test)` counter (or a `debug_assertions` statistic) beside D6 lets the witness test assert that the path ran, turning coverage from a claim in a comment into a checked fact (B5-3).
