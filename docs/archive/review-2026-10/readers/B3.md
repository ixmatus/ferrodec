# Reader B3 report: the I/O boundary on all three formats (Wave 3)

Baseline gate: `git rev-parse HEAD` = `ba92f29cdfb1f9870758ca46c73509edb0891d9e` (matches). I wrote nothing under the repository (the untracked files `git status` shows are other readers' and the coordinator's). All cargo runs used `CARGO_TARGET_DIR=.../scratchpad/target-B3`. Reproducers live in `scratchpad/B3/probe/` (a scratch crate with path deps on the three format crates, features `fmt,binary-float,serde,num-traits,ops,dpd`; binaries `b3probe`, `bidjson`, `nt`, `nanprop`, `engp`, `sumz`) and `scratchpad/B3/py/` (Python drivers: `parse_diff.py`, `int_diff.py`, `f2d_diff.py`, `d2f_diff.py`, `fmt_diff.py`, `bits_fuzz.py`, `dpd_check.py`, `timeit.py`). Build: `cd scratchpad/B3/probe && CARGO_TARGET_DIR=../../target-B3 cargo build --release`.

## Threat model (extra deliverable)

- **String parse** (`parse_str`, `FromStr`, `Num::from_str_radix`, serde default `Deserialize`, `serde_bid` string fallback, and transitively `from_f64`). Supplier: anyone who controls text the application parses (form fields, JSON, CSV, config, a calculator keystroke stream). Worst outcomes: unbounded CPU per call (found on the siblings: B3-1), a panic (none found: 0 panics in 40,000 parse differential cases plus debug-build runs), a value that parses back differently (none on finite values), and a non canonical encoding minted at the boundary that then escapes into arithmetic (found on the siblings: B3-5). Silent rounding and silent overflow to `Infinity` through `FromStr` and serde are by design (status discarded) and are design notes, not findings.
- **Bits decode** (`from_bits`, `from_dpd_bytes`, `serde_bid` integer path). Supplier: anyone who controls stored or transmitted bytes (database column, wire frame, file). Worst outcomes: a panic in a formatter or converter on a non canonical pattern (none found: 90,000 random and structured patterns through `Display`, `{:e}`, `{:E}`, `{:.3}`, `{:.3e}`, `engineering`, `fixed_preferred`, `canonicalize`, all clean), a string that does not parse back (found for non canonical NaN payloads: B3-7), and non canonical payloads propagating through arithmetic (seen; lead to the ops reader). DPD decode is total and canonical on all 1,024 declets.
- **Serde.** Supplier: the serialized document. Work is bounded by the string parser (so B3-1 applies to Decimal64 and Decimal32 `Deserialize`). `serde_bid` on Decimal128 cannot read back what it writes in JSON (B3-6).
- **Float conversion** (`from_f64`, `from_f32`, `to_f64`, `to_f32`, `TryFrom`). Supplier: any binary float the application holds, including one decoded from untrusted bytes (sNaN patterns). Worst outcomes: a wrong decimal value (found on the siblings under nearest, and on every format under directed modes: B3-4), a missing exception flag (UNDERFLOW never raised: B3-3). No panic path: the `expect` calls at `src/convert/binary.rs:147,197,265` are unreachable for canonical finite inputs (Display of a finite Decimal128 is at most 42 bytes in a 64 byte buffer).

### B3-1: sibling parse costs O(10^9) for a 10 byte exponent

Command (release build of `scratchpad/B3/probe`):
`/usr/bin/python3 scratchpad/B3/py/timeit.py scratchpad/target-B3/release/b3probe scratchpad/B3/py/slow_cases.txt` (one process per line, wall time):

```
  0.003s  P 128 TZ 1E-1000001                       -> ... UXC 0E-6176
  2.677s  P 64 TZ 1E-1000001                        -> 0000000000000000 UXC 0E-398
  2.698s  P 64 TZ 12345678901234567890123456789012345E-1000001 -> ... UXC 0E-398
  0.005s  P 64 TZ 12345678901234567890123456789012345E-999999  -> ... UXC 0E-398
  2.690s  P 32 TZ 1E-1000001                        -> 00000000 UXC 0E-101
  0.003s  P 32 TZ 12345678901234567890123456789012345E+1000001 -> 77f8967f OX 9.999999E+96
```

Through serde (`scratchpad/B3/py/dos.txt`): `JSON 64 "1E-1000001"` 2.580 s, `JSON 32 "-9e-99999999999999999999"` 2.581 s, `JSON 128 "1E-1000001"` 0.004 s. A debug build takes about 6.6 s per call (first observed when the differential stalled). Values and flags are correct; only the cost is wrong.

Trace: `parse_str_inner` saturates the exponent field to `EXPONENT_FIELD_SATURATED = 2_000_000_000` (ferrodec-decimal64/src/convert/parse.rs:392), so `unbiased_exp ≈ −2·10^9` (:415) reaches `round_and_pack_finite` (ferrodec-decimal64/src/ops/round.rs:62). There `subnormal_excess = qmin − unbiased_exp ≈ 2·10^9` (:105), `excess` takes it (:106), and `drop_excess_digits(coef, excess, ...)` (:110) runs `while i < n { coef % 10; coef /= 10; ... }` (:210-219) two billion times, long after `coef` reached zero. The root does not have this loop shape (0.003 s). Positive exponents overflow before reaching the loop. The d32 copy is ferrodec-decimal32/src/ops/round.rs:208-221.

The sibling `parse_str` rustdoc (ferrodec-decimal64/src/convert/parse.rs:140-164) names "unbounded work on a long input" as one of the three outcomes to defend and says "The cost is bounded by input length, not by input value." The 10 byte input falsifies that sentence. ADR-0057 chose the 2·10^9 sentinel for i32 headroom and never priced the downstream loop.

Why the stack missed it: the decTest runners replay the 11 `e-999999999` rows per sibling (`ddBase.decTest`, `dsBase.decTest`) and compare value and flags only, so they pass slowly (roughly 11 × 2.6 s release, more in debug) and nobody times them. The fuzz `parse` target would catch it only with a timeout below libFuzzer's 1,200 s default, and the fuzz crates have not built since 2026-05-09 (C5-3). The trust table row "strings, from_bits, ... (self-consistency)" asserts round trips, not cost.

### B3-2: engineering `{:.N}` prints fabricated digits

Command: `cd scratchpad/B3/probe && CARGO_TARGET_DIR=../../target-B3 cargo run --release --bin engp`

```
     12345: d128 {:.2} eng=12.30E+3 | d64=12.30E+3 | d32=12.30E+3 | {:.2e}=1.23e+4
    123456: d128 {:.2} eng=123.00E+3 | d64=123.00E+3 | d32=123.00E+3 | {:.2e}=1.23e+5
  0.012345: d128 {:.2} eng=12.30E-3 | d64=12.30E-3 | d32=12.30E-3 | {:.2e}=1.23e-2
 98765E-20: d128 {:.2} eng=988.00E-18 | d64=988.00E-18 | d32=988.00E-18 | {:.2e}=9.88e-16
```

Oracle: exact decimal arithmetic. `98765E-20` is `987.65E-18`. At two fractional digits the engineering string should be `987.65E-18`; at three significant digits it would be `988E-18`. The output `988.00E-18` claims five significant digits and is wrong in the last two.

Trace: `format_to` (src/convert/format.rs:274) sends `Notation::Engineering` with a precision through `quantize_to_scientific_precision` (:284 → :218), which keeps `p + 1` significant digits (the scientific layout's need). `format_engineering_into` then puts `shift + 1` (up to three) digits before the point and pads the fraction to `target_frac = precision.unwrap_or(frac_natural)` (:645) with zeros (:648-650). For a two or three digit integer part the padding replaces real digits that the quantize step already discarded. Same code at ferrodec-decimal64/src/convert/format.rs:238/:532 and ferrodec-decimal32/src/convert/format.rs:237/:540.

ADR-0058:64-66 justifies keeping this shape with "the precision path already quantizes the mantissa for that layout", which is the false premise, and ADR-0058:93 advertises `{:.N}` as the way to get unconditional engineering exponential output, which makes this the documented route into the defect.

Why the stack missed it: no test pins `{:.N}` on the `Engineering` adapter (grep finds none in src or tests of any crate); the decTest `toEng` vectors have no precision concept; the trust table's formatting rows are self-consistency checks that never compare a rounded rendering against an exact oracle.

### B3-4: `from_f64` double rounds on the siblings and ignores direction everywhere

Command: `scratchpad/target-B3/release/b3probe < scratchpad/B3/probe/f2d.txt`

```
F2D 64  NE 43c957633e24d15b -> 2e44f98ae0546300 X 3.652074584957696E+18
F2D 32  NE 3e212c1218a7bcdd -> 256e80fe X 1.999102E-9

```

Exact values (CPython `Decimal(float)`): `0x43c957633e24d15b` is `3652074584957695488`, so the 16 digit nearest is `3.652074584957695E+18`; `0x3e212c1218a7bcdd` is `1.99910149999999991306…E-9`, so the 7 digit nearest is `1.999101E-9`; `0x3fb999999999999a` is `0.1000000000000000055511151231257827…`, so TowardPositive must return a value at least that large and must raise INEXACT.

Differential `scratchpad/B3/py/f2d_diff.py` (oracle: CPython `Context(prec=P, rounding=rm).create_decimal(Decimal(x))`): among inputs whose shortest string is longer than P, d32 differs from the correctly rounded value in 540 of 6,052 cases and d64 in 126 of 2,448 (the generator aims at P digit midpoints). The cases where the shortest string fits P digits differ by design (ADR-0056 decision 1: `from_f64(0.1) = 0.1`).

Trace: `from_f64` writes `{x:e}` (the shortest round trip string, itself a rounding of the binary value) into a buffer (ferrodec-decimal64/src/convert/binary.rs:244) and hands it to `parse_str(s, rm)`, which rounds that string to 16 digits (:257). Two roundings, the first always to nearest. Root: same at src/convert/binary.rs:265; its 34 digit coefficient holds every shortest string, so only the directed mode defect applies there.

ADR-0056:44-51 says the switch to `{:e}` removed "the double-rounding hazard" and that a value whose shortest form exceeds the precision "still rounds once". The first rounding (binary to shortest) is still there.

Why the stack missed it: the ADR-0056 tests pin `0.1` under NearestEven; the trust table rows for `binary_float` are self-consistency (from_f64 then to_f64 round trips, which a double rounding preserves); no oracle compares `from_f64` against the exact binary value.

## Least sure

- **Other public callers of the sibling `drop_excess_digits`.** I proved reachability only from the parser. `round_and_pack_finite` is shared; any public operation that can hand it an exponent far below `qmin` (a `scaleb` with an unclamped `i32` count, `quantize` with an extreme target, `from_parts`) would inherit B3-1. Command to check: `ast-grep --lang rust -p 'round_and_pack_finite($$$)' ferrodec-decimal64/src ferrodec-decimal32/src` and time each caller with an extreme argument. Belongs to the ops reader.
- **Non canonical NaN propagation through arithmetic.** `nanprop` shows a non canonical payload survives `add` and `mul` on all three formats (root via `from_bits`). Whether §3.5.2 / §6.2.3 require operations to emit canonical results is the ops reader's call (src/ops/nan_propagate.rs and twins); I only established the input path.
- **`{:.N}` with `N > i32::MAX`.** `quantize_to_fixed_precision` computes `-(precision as i32)` (src/convert/format.rs:212), which overflows (a debug panic) at `N = 2^31`. Rust 1.87 and later cap format precision at `u16::MAX`, so this is reachable only on the 1.84 to 1.86 MSRV window with a runtime `{:.*}` argument. Not run.
- **Tininess after rounding for `to_f64`.** I asserted the smallest normal boundary row misses UNDERFLOW under both tininess conventions; I did not compute the after rounding classification for every row in that band, only the subnormal results.
- **Directed `from_f64` on the root at large magnitudes.** I showed the direction defect at `0.1`; I did not sweep how often it fires (it fires for every f64 whose shortest string is not its exact value, which is almost all non dyadic-small values).
- **serde formats other than JSON and bincode** (MessagePack, CBOR, YAML) were not run; the B3-6 shape applies to any human readable format whose `deserialize_any` cannot deliver a `u128`.
- **`from_str_const` panic texts** were read, not compiled against each failure.
- **`from_i128` / `from_u128` past P digits** (root `round_and_pack_finite` on a `U256`; siblings pre-reduce to `u64` with sticky) were traced, not run against an oracle. Command: extend `int_diff.py` with `from_i128` rows against `Context(prec=P).create_decimal(n)`.

## Found clean

- **Root and sibling string parse** (src/convert/parse.rs `parse_str_inner`, `match_special`, `parse_nan_payload`, `parse_literal`; twins): `parse_diff.py`, 20,000 generated strings per seed across formats and five rounding modes (leading zero runs to 3,000, fractional zero runs to 7,000, 30 to 200 digit mantissas, sticky tails, exponents around every format boundary, `i32`/`i64` overflow and saturation, zero cohorts, NaN and infinity spellings, the malformed list in the edge table, NUL, non ASCII) against CPython `decimal` for value, cohort (string compare of toSci) and the Overflow, Underflow, Inexact and Clamped flags. Results: seed 1, 224 mismatches; seed 2, 249 mismatches; every one is a sibling NaN payload in the non canonical gap (B3-5); zero mismatches of any other class on any format, so finite values, cohorts, saturation, zero clamping, specials and syntax errors all agree with libmpdec. Debug build runs found no arithmetic overflow panic. Blind spot: CPython accepts some spellings GDA rejects (whitespace, Unicode digits), which I excluded by rule; Subnormal and Rounded flags are not modelled by ferrodec and were not compared.
- **toSci and toEng rendering** (format.rs `format_finite`, `format_zero`, `format_engineering_into` without precision; twins): `fmt_diff.py`, 24,000 exactly representable values per run (zeros at every quantum, every residue mod 3, the format extremes) against `str(Decimal)` and `to_eng_string()`: 0 mismatches. ADR-0058 zero rows correct. Blind spot: precision and width specifiers (where B3-2 and B3-8 live).
- **Formatter totality on `from_bits` input** (format.rs all notations, `{:.3}`, `{:.3e}`, `canonicalize`): `bits_fuzz.py`, 90,000 random and structured patterns (Form B, Form A above `10^P`, special field patterns): no panic; every finite and infinite value round trips bit for bit to `canonicalize()`. The 32 `expect`/`unreachable` sites in format.rs are unreachable from the public API by this evidence plus reading (each `from_utf8` sees ASCII digits; the `unreachable!` at :501 follows an exhaustive early return; `write_digits` sees only coefficients below `10^P` because `classify_bits` routes larger ones to `Zero`). Blind spot: random sampling, not proof; `{:.N}` with huge `N` not run.
- **Integer conversions** (src/convert/int.rs and twins): `int_diff.py`, 30,000 values × 6 target types × 5 modes = 180,000 conversions against CPython `to_integral_value` plus range checks: 0 mismatches. The semantics are §5.8 `convertToIntegerExact` (Inexact on any fraction, Invalid with a saturated value on out of range, NaN and infinity, `-0.4 → 0` without Invalid for unsigned). The `debug_assert_eq!(cur, 0)` at src/convert/int.rs:327 holds by construction (the loop divides at least `digits` times when `drop >= digits` and breaks only at `cur == 0`); release code does not rely on it. Blind spot: the API offers no non exact `convertToInteger` form; callers mask INEXACT themselves (design note).
- **DPD codec** (src/dpd.rs and twins): `dpd_check.py` against a decode table derived from IEEE 754 Table 3.3: all 1,024 declets at two positions on each format decode to the table's digits and re-encode to the canonical declet (6,144 checks, 0 bad), including the 24 non canonical declets. The conformance runners already replay `dqEncode`/`ddEncode`/`dsEncode`. Blind spot: combination field edge cases rely on the vector files.
- **`to_f64` values** (all formats): `d2f_diff.py`, 18,000 decimals: every value equals CPython `float(Decimal)` (correct rounding), and INEXACT is exact outside the subnormal range. Blind spot: directed modes (B3-11) and UNDERFLOW (B3-3).
- **`from_f64` on the root at nearest**: correct rounding of the shortest string, as ADR-0056 decides; NaN sign kept; sNaN raises INVALID (read; spot checked).
- **`Neg` on NaN**: flips the sign, raises nothing, keeps the payload (`-NaN5`, `-sNaN`), which is §5.5.1 `negate` exactly.

## Design notes

1. **Parse status is thrown away at three public doors** (`FromStr`, serde `Deserialize`, `Num::from_str_radix`), so an attacker string like `"1E+99999"` deserializes to `Infinity` and a 40 digit string rounds silently. A `TryFrom<&str>`-style strict parser (error on Inexact or Overflow) would let services that ingest untrusted decimals refuse rather than coerce. Evidence that would make it a finding: a documented contract that serde input is exact.
2. **`ParseDecimalError` vs GDA Conversion_syntax**: the error type is good Rust, but `from_str_const`'s exponent bound and `CoefficientOverflow`'s literal length cap are two different ceilings on what parses; a single `MAX_LITERAL_LEN` type level constant shared by the three crates would replace the three hand synchronized copies ADR-0057 already worries about.
3. **The float boundary wants an exact kernel**, not string round trips: the root already has `U256`; an exact `m·2^e ↔ c·10^q` converter would discharge B3-3, B3-4 and B3-11 together and remove the `expect` panics. Evidence: the three findings share the string path as root cause.
4. **`Display` should render into a buffer and pad**: the same change fixes B3-8 and gives one place to enforce "payload only if canonical" (B3-7).
5. **`ToPrimitive` and `%` encode two per crate policy choices** (rounding for conversions, remainder flavour) that generic code cannot see; a single documented policy table in the num-traits module rustdoc, shared by the three crates, would turn B3-9, B3-10 and B3-12 into checkable statements.
