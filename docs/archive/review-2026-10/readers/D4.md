### D4-1: the §7.4 CLAMPED attribution starts in the ADR

Command and output (excerpt):

```
$ git grep -n "§7\.4" -- ':!docs/archive' | grep -i -c clamp        -> 64
$ git grep -l "§7\.4" -- ':!docs/archive' | xargs grep -l -i clamp | wc -l   -> 46

docs/decisions/0048-clamped-fidelity-and-bid-residual.md:8:IEEE 754-2019 §7.4 / the General Decimal Arithmetic specification define CLAMPED as
docs/references/ieee-754-2019.md:40:§6.2.3 NaN propagation rule, §7 exceptions and the §7.4 underflow and
CHANGELOG.md:143:  §7.4 overflow disposition in release; huge integer exponents now
docs/decisions/0057-parse-exponent-saturation.md:16:per §7.4; only a malformed string is a conversion error.
```

The code's own clause usage (tally of `§7.x` in `src` and `ferrodec-*/src`): `§7.5` names underflow at 9 sites, `§7.4` names overflow at 2 and Clamped at 9. One clause number cannot mean both, and the tree uses §7.5 for underflow, so the registry entry's "§7.4 underflow" is wrong by the tree's own convention. The Clamped condition's actual home, confirmed on the archived GDA page `https://web.archive.org/web/20260910090326/https://speleotrove.com/decimal/daexcep.html` (fetched 2026-10-09): "Clamped. This occurs and signals clamped if the exponent of a result has been altered in order to fit the constraints of a specific concrete representation." I cite §7's clause list (7.2 invalid, 7.3 division by zero, 7.4 overflow, 7.5 underflow, 7.6 inexact) from the proxy literature, not from the paywalled text, so the IEEE side is traced.

Generation path for the registry text: `references_integrity.rs:137` holds the gloss as a string literal; `registry_status_flags_pinned` (lines 99 to 159) renders `- \`{name}\` (bit {bit}, predicate \`{predicate}\`): {gloss}.` with only `bit` computed from `Status` (`flag.bits().trailing_zeros()`), and asserts byte equality with the block between the markers in registry-status-flags.md:30-37 (`references.rs:393-410`). So the document is "generated" from a second hand written copy of status.rs:21, and fixing status.rs alone leaves the test literal and the document in agreement with each other and wrong. The same prose error sits ungenerated at registry-status-flags.md:27 ("six IEEE 754-2019 §7 flags").

Other generated blocks and their sources of truth: `rounding-modes` (registry-rounding-modes.md:29-35, test lines 57-90): variant population from an exhaustive match, every string a literal; I checked the five IEEE attribute names (roundTiesToEven, roundTiesToAway, roundTowardZero, roundTowardPositive, roundTowardNegative) against the §4.3 attribute names: correct. `ieee-classes` (registry-ieee-classes.md:28-39, test lines 162-218): population from the exhaustive match, glosses literal; consistent with `IeeeClass`. No other generated block exists in the tree (`git grep "BEGIN GENERATED"`).

Type that would have made the sentence unnecessary: a `#[non_exhaustive]` provenance enum on each flag (`Provenance::Ieee754(Clause)` / `Provenance::Gda(Condition)`) rendered into both the rustdoc and the registry block, so the clause appears in exactly one place.

The MIT grant's condition (the notice "shall be included in all copies or substantial portions") and Apache-2.0 §4(a) (give recipients a copy of the License) travel with the package, so a downstream vendor of `ferrodec-ieee-*.crate` receives code with no license text. The crates are yanked today, which narrows the exposure and makes this a pre publish fix. Not a legal opinion; the record should state Parnell's decision either way.

## Design notes


1. **Citations as data.** Every finding in this report except D4-6 is a fact stated twice (a clause in a comment and in an entry, a status in an entry and in a bead, a source in code and in a `consumers` list) with nothing comparing the copies. A `ref: <slug> §<clause>` tag in comments, harvested by the guard, makes the registry the single source and turns D4-1, D4-2 and D4-8 into test failures. Evidence that would make it a finding: one more drift of the D4-1 kind after the sweep.
2. **Generated means derived.** The three "generated" blocks derive less from the types than ADR-0052 suggests. Rendering names with `stringify!` and glosses from the items' own doc attributes (or a `const DOC: &str` per flag) would make the rustdoc and the registry one string.
3. **Failure entries keyed to beads.** A failure entry with `bead: fd-xxx` and `fix: <commit>` fields, checked against the local beads export at test time when present, stops the museum going stale between arcs (D4-4).
4. **Oracle versions as registry facts with artifact witnesses.** Corpora are the durable output of the oracles; each `.prov` header stamping the oracle and version, with the registry entry listing the stamped set, is the cheap insurance C5-13 asked for.
5. **Package manifests as a reviewed surface.** `include` lists per crate would make what ships to crates.io an explicit, diffable decision (D4-6), and would have kept 224 review files out of the root crate.
