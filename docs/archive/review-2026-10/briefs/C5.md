# Reader C5: tooling, scripts, and continuous integration (Wave 1)

Lens: can a maintainer in 2040 regenerate every corpus and rerun
every gate from the tree alone, and do the two gate instruments
(the local battery and GitHub CI) select the same things? Ten weeks
of red push CI behind a green battery is the failure this lens
exists for; Phase 0 of this review fixed the four causes and added
parity lanes, and you audit the result.

## Scope (you own these)

- `tools/*` (18 scripts: the Arb corpus generators, the certifiers,
  the campaign launchers and freezer, the exhaustive sweep, the
  differential oracle, the constant generators, the Liouville probe,
  and `tools/gate_battery.sh`).
- `.github/workflows/ci.yml` and `verification.yml`.
- `ferrodec-campaign/src/{sample,sweep,prng}.rs`, `src/bin/sweep.rs`
  (the sweep driver; `margin.rs` belongs to a Wave 2 reader).
- `fuzz/` (root) and `ferrodec-decimal{64,32}/fuzz/`.
- `verus/EXPERIMENT.md`.
- `rust-toolchain.toml`, the workspace `Cargo.toml` lint block.

Governing documents: ADR-0026, ADR-0033/0034 (what the sweep tools
promise), ADR-0042, ADR-0052, ADR-0059 (the lanes it names: force
escalate, ladder audit, force adjudicate, force rung 3, telemetry),
`docs/testing.md` on every lane and corpus; the Phase 0 commits
`0c5914d`, `163ac2c` on this branch (what changed and why).

## Checklist

1. **Script discipline.** Every shell script: `set -o pipefail`
   present (a `cargo test | grep` pipeline masked a real kernel
   defect once); the script `cd`s to its own computed root before
   building (a launcher once built into the caller's directory and
   no-op'd 160 shards); resumable scripts audit completeness
   (checkpoint count equals shard count) rather than trusting "the
   pool finished". Every Python tool: deterministic for a fixed seed,
   seed recorded in output headers, no wall clock in the output
   except as a header.
2. **Corpus reproducibility.** `tools/freeze_campaign_corpus.py`
   rerun on the archived S2 outputs under
   `~/.local/share/ferrodec-campaign/` (if present) is byte identical
   to `tests/vectors/transcend/campaign/`; if the outputs are absent
   say so (that is itself a durability finding). Each generator
   names the tool version and parameters in its `.prov` output.
   `tools/gen_argred.py:1` targets `src/math/argred.rs`, which is now
   a shim: where does the table it generates actually live, and does
   the script still regenerate it byte for byte?
3. **Environment durability.** No `requirements.txt`, `pyproject`,
   nix shell, or version pin exists for the Python tools; the Arb
   tools import python-flint from a sister project's venv
   (`~/.cache/pfloat-arb-oracle/venv`); `verification.yml` installs
   mpmath unpinned. State the exact dependency set and versions the
   tools need (read the imports), and what a fresh machine needs to
   run each tool.
4. **CI and battery selection parity, after Phase 0.** Build the
   full matrix: for each (package, feature set, target, command) CI
   runs, which battery lane runs the same, and vice versa. Known
   gaps to confirm or refute: `force_rung3` and `telemetry` in no CI
   lane; `ferrodec-campaign`'s test in neither; Kani absent from the
   battery before Phase 0 (now a lane); `thumbv8m.main-none-eabi` in
   `rust-toolchain.toml` but never built; `ci.yml` labels d32/d64
   "in development"; the `verification.yml` comment claiming its
   lanes mirror the battery; MSRV 1.84 checked for the root only.
5. **`verification.yml` content** against what `README.md` and
   `docs/testing.md` say runs weekly; what the campaign smoke lane
   actually exercises at tiny N.
6. **Fuzz.** The fuzz crates: is `fuzz/Cargo.toml` an orphan (no
   `[workspace]` table, no root `exclude`)? Build each with the
   installed nightly if one exists (`cargo +nightly fuzz build`), or
   report that none is installed. Do the targets' assertions match
   what README.md claims for them?
7. **The battery itself.** `tools/gate_battery.sh` after `163ac2c`:
   lane by lane, does each run what its comment says; does the
   `members` lane's root `--all-features` run include the Python
   differential and what does that need; is anything run twice; is
   the preflight honest.
8. **Vector sums.** Every vector directory has a `SHA256SUMS` and a
   checker that runs by default; name the exceptions.

## Deliverable in addition to the schema

The **parity matrix** (item 4) as its own section, and an
**environment manifest** (item 3): tool, interpreter, imports,
versions observed, where they come from on this machine.
