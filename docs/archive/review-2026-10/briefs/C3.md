# Reader C3: clarity and pragmatism, `ferrodec-transcend` (Wave 4)

Lens: principled engineering. Is the code clear, pragmatic and well
written, and does each piece of structure earn its keep? You judge
shape, duplication, naming, comment accuracy and dead weight; the
correctness readers (A1 to A5, Wave 2) have already judged values, and
their reports under `readers/A*.md` and the verdicts in
`wave2-verification.md` are your inputs. Shape opinions become findings
only with the evidence named in the common frame.

## Scope (yours alone in this wave)

- `ferrodec-transcend/src/**` (23,036 lines, 27 files, no `tests/`
  directory, 172 inline tests): read for structure, not for values.
- The root shims `src/math/{argred,extended}.rs` and the
  `#[allow(unused_imports)]` they carry (C4 owns the rest of `src/`).

Governing: the workspace lint policy in the root `Cargo.toml`
(`[workspace.lints]`), ADR-0059 to 0061 (the design the code should
express), `docs/decisions/README.md`, the Wave 2 design notes (A1 to
A5, each report's last section), the Phase 1 `counts.md` row for the
crate (241 `as` casts, 28 `expect(`, 9 `panic!`, 3 `unreachable!`).

## Checklist

1. **The extended trio** (`extended.rs` 2,401 lines, `extended2.rs`
   1,441, `extended_dyn.rs` 2,284). For each function present in all
   three: the line count triple, whether the bodies differ beyond width
   constants (use `mirror_summary.md` and regenerate the diffs with
   `mirror_diff.sh`), and `git log -L` evidence of a fix that landed in
   one copy and not the others. Wave 2 found the shape costs real
   defects: the Newton seed defect is in all three copies
   (P1B-2, A4-6, A5-6), the `newton_steps` derivation exists only in
   `extended_dyn` (fd-k9t), the doc drift is per copy (A3-8). Quantify
   the drift cost in those terms and state what one generic
   implementation would need (a width parameter, a const generic, or
   the arena) and what it would cost on the fixed rungs.
2. **`exact.rs` as one 3,800 line file.** Module boundaries the file
   already implies (per family classifier blocks, shared helpers, the
   pi family in `exact_pi.rs`); the four copies of the
   `2^α 5^β t → (coef, w)` assembly with identical 127/55 gates (A1
   design note 2); the 46 items compiled dead under `trig-pi` alone
   (A1-1); the header that lists twelve functions and counts fifteen
   (A1-3).
3. **Literals that should be one constant.** The cancellation depth
   `33` appears in more than eight places across `argred.rs` and
   `ladder.rs` and is false (P1B-1, A4 design note 1); the budget units
   are bare `u128` (A3 design note 3); gate constants are borrowed from
   `exp` by neighbours (A5-1). List each literal family with its sites.
4. **Function length and concern mixing.** Every function over 80
   lines: long because the algorithm is, or because concerns mix
   (dispatch, classification, delivery, telemetry in one body). Name
   the ones that mix.
5. **Rustdoc versus code.** Stale markers (`lib.rs:77` "until M8 wires
   the ladder", `format.rs:4` "Decimal64 / Decimal32 later", the
   catalog note rewritten in Phase 0); every doc claim Wave 2 marked
   false (A3-8, A4-5, A5-10, A3-4's itemization, A4-3's certificate
   comment) as a class: how many rustdoc paragraphs state a number the
   code does not compute.
6. **Panics and `expect(`.** Every `expect(` message (28), `panic!` (9)
   and `unreachable!` (3): is the message a proof or a hope; which are
   reachable (A3-9's `parse_str` is `pub` and panics on invalid
   characters; `from_format` panics on an infinite seed, P1B-2).
7. **Casts.** The 241 `as` casts under a workspace wide allow of the
   cast lints: sample fifty across files and classify (bounded by a
   visible invariant, bounded by a comment, or unbounded); report the
   fraction with no stated bound.
8. **Dead code and `#[allow]`.** Every `#[allow]` and `cfg_attr(...,
   allow(dead_code))` in the crate (Phase 0 added 73 to `ladder.rs`
   to keep the per cluster feature builds compiling): which hide real
   dead items and which paper over a feature graph that should be
   simpler (D1 owns the graph; you supply the evidence).
9. **Naming across rungs.** `Extended`, `Extended2`, `ExtendedDyn`,
   `rung_budget`, `dynamic`, `run3`, `round_guarded`,
   `round_adjudicated`: does a reader of `ladder.rs` learn the model
   from the names, or need the ADR open beside the file.
10. **Test placement.** 172 inline tests and no `tests/` directory on
    a 23k line crate, with the real format tests living in the three
    format crates: what belongs in a transcend `tests/` directory (the
    forwarding adapter A1 built would make real format tests possible
    inside the crate).
