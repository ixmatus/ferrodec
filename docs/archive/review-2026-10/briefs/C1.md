# Reader C1: test quality, the transcendental surface (Wave 1)

Lens: are these tests meaningful and accurate? A test earns its place
when a plausible defect in the code it names would turn it red. Your
output is the instrument trust table for the transcendental surface,
which every later correctness reader will cite when answering "why
did the stack miss it".

## Scope (you own these; nobody else in this wave reads them)

- Every `tests/*.rs` in the root crate, `ferrodec-decimal64/tests/`,
  and `ferrodec-decimal32/tests/` whose file name contains any of:
  `transcend`, `exact`, `pi`, `ladder`, `campaign`, `anchor`,
  `planted`, `lsz`, `directed`, `crosscheck`, `differential`;
  plus `property_transcendentals.rs` where it exists.
- The inline `#[cfg(test)]` modules of `ferrodec-transcend/src/*.rs`
  (172 tests) and `ferrodec-transcend/src/mock_format.rs`.
- `ferrodec-test-support/src/frozen.rs` (the `EXPECTED_BUCKETS_*`
  pin tables and corpus loaders), `transcend_oracle.rs` (the
  astro-float faithful checker), `differential.rs` (the Python
  harness).
- `ferrodec-campaign/tests/margin_lockstep.rs` and
  `ferrodec-campaign/tests/vectors/`.

Governing documents: ADR-0025 (metamorphic identities), ADR-0026
(independent oracles), ADR-0033/0034 (exhaustive d32), ADR-0042
(fixture integrity), ADR-0050/0051 (anchor bands, residual seam),
ADR-0059 (the ladder and its lanes), ADR-0060, ADR-0061;
`docs/testing.md` throughout; the June report's "Verification
infrastructure findings" and "Why the stack missed the confirmed
bugs".

## Checklist

For each test file, answer in the trust table: what does it
actually assert, against what reference, and what defect class
would NOT turn it red.

1. **Tautology.** Metamorphic identity tests that route both sides
   through the kernel they test (ADR-0025 "tautology creep"): name
   each identity and whether a shared-kernel error cancels.
2. **Floors versus pins.** Every count assertion: is it an exact
   per bucket pin or a floor (`>=`, `> N`, `len() > 500`)? List every
   floor with its line. The project rule is exact per bucket
   ([[feedback-regression-guard-exact-match]]); a floor admits a
   compensating regression.
3. **Oracle correlation.** astro-float asserts the faithful (at most
   1 ULP) contract, so a 1 ULP directed misround passes by
   construction (June finding). For each suite, which oracle decides
   correctness, and is that oracle independent of the kernel under
   test? The cross precision checks (`d128_crosscheck.rs`,
   `d64_crosscheck.rs`) share the kernel: say exactly what they can
   and cannot catch.
4. **Vacuous assertions.** Tests that assert only `is_ok()`, "no
   panic", or that a status is some value without checking the
   result; proptest strategies whose ranges cannot reach the band the
   test name promises (coefficient digit counts, decade ranges); the
   `#[ignore]` discipline (which ignored tests ever run, where).
5. **Drift between the three formats.** Test bodies duplicated across
   root, d64, d32 that have diverged in what they assert; a
   `property_*` file present in one crate and absent in another
   without a stated reason.
6. **`.proptest-regressions`** committed only in the root crate: what
   regressions do they pin, and do the siblings lack equivalents?
7. **`mock_format.rs`.** The test double behind transcend's inline
   tests: does its rounding and packing match the real formats? If it
   differs, say which inline test verdicts are hollow.
8. **The pin tables in `frozen.rs`.** Hand maintained
   `EXPECTED_BUCKETS_*`: are they exact per (function, mode, file)?
   Does any loader silently skip malformed rows (the June
   `strip_comment` class)?
9. **Documented counts.** The planted corpus is described as "36
   operations × 6" in README.md and "36 operations × 30 rows" in
   CHANGELOG.md; which is true at the loader?
10. **Campaign test** (`margin_lockstep.rs`, 90 lines): what does it
    pin, and is `ferrodec-campaign/tests/vectors/margin_lockstep.txt`
    hash pinned anywhere?

## Deliverable in addition to the schema

A **trust table** as its own section: one row per test file or
inline module: file; what it asserts; reference used; exact pin,
floor, or none; independent of the kernel (yes/no/partly); the
defect class it cannot see. This table is handed to Waves 2 and 3.
